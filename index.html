Let’s work through it together

How does memory
make room?

Paging algorithms, explained one decision at a time.

“Imagine your desk holds only three books. You need a fourth book to continue your work. Which book would you put away?”

Think first: the oldest book on your desk, the one you have not used recently, or the one you will not need for a while?

Today we will connect those choices to FIFO, LRU, and Optimal page replacement.

Teacher notes · how to explain this

Give students 30 seconds to suggest a rule. Accept different answers. Say: “Each rule makes sense, but each uses different information. A computer faces a similar choice when its available memory fills up.”

01 / Connect the analogy

The desk is memory. The books are pages.

The bookshelf → storage

Many pages can be kept on backing storage. Bringing a page into memory takes time.

The desk → physical memory

Only a limited number of pages can be resident at once.

A desk space → a frame

Each frame holds one page. Pages and frames have the same fixed size.

“We divide a program’s virtual memory into fixed-size pages. We divide physical memory into matching slots called frames.”

Ask the class: if we have three frames, how many pages can they hold at one time? Three.
Teacher notes · how to explain this

This is a simplified analogy. A page is a block of virtual memory, not an entire program. Keep the terms separate: page means the data block; frame means the physical slot.

02 / Read the first image

How do we find a page?

“Look at Page 0 on the left. The middle column says it is in Frame 2. So we go to Frame 2 on the right. Page 1 has no resident frame, so accessing it would cause a page fault.”

Quick check: where is Page 2? Point to its mapping, then its frame. Frame 0.
Teacher notes · how to explain this

Trace the first mapping with your pointer. Ask a student to trace the second. Explain that this diagram simplifies address translation: the offset within the page stays unchanged.

03 / Explain the problem

A page fault means “not here yet.”

“The CPU asks for Page 4, but it is not in memory. The operating system handles the page fault. Because our frames are full, it chooses a page to remove, brings in Page 4, and lets the instruction continue.”

A hit means the page is already resident. A fault means it is not resident. A fault is not automatically a program error.

Teacher notes · how to explain this

Ask: “Does every page fault remove another page?” The answer is no: empty frames can be filled first. Invalid accesses are a separate issue; this lesson assumes valid references.

04 / Set up one shared example

Read the reference string one number at a time.

Three empty frames. Requests: 1 → 2 → 3 → 1 → 4 → 1 → 2 → 3

“Each number is the page requested next. We process the numbers from left to right. The first request to Page 1 causes a fault because memory starts empty.”

These first four requests are identical for all three policies.

Teacher notes · how to explain this

Do not introduce all three rules at once. Establish the shared starting state, then compare one replacement decision per slide. Keep frame positions fixed so students can see exactly what changed.

05 / First rule · FIFO

Who has been here the longest?

“FIFO means First In, First Out. Page 1 entered first, so it leaves first. We accessed it again, but a hit does not move it to the back of the FIFO queue.”

Ask: why does Page 1 leave even though we just used it? Because FIFO tracks arrival, not recent use.
Teacher notes · how to explain this

Point to the oldest entry, then to the changed frame. Say: “Only Frame 0 changes. We have now had four faults in five requests.”

06 / Second rule · LRU

Which page have we ignored the longest?

“LRU means Least Recently Used. Page 1 was used at position 4, so it is recent. Page 2 was last used at position 2, earlier than the others. This time, Page 2 leaves.”

Ask: what changed when Page 1 was a hit? Its last-used time changed, even though the frames did not.
Teacher notes · how to explain this

Return to the same starting frames, 1, 2, 3. Do not continue from FIFO’s replacement. Stress that LRU uses the past; it does not predict with certainty.

07 / Third rule · Optimal

Which page will we need furthest in the future?

“For this classroom example, we can see the remaining requests: 1, 2, 3. We keep the pages needed soon and remove Page 3, which is needed furthest ahead. A page never used again would be an even better victim.”

Ask: why can we demonstrate Optimal on paper but not generally use it exactly in a running system? We do not know future requests.
Teacher notes · how to explain this

Explain that Optimal gives a minimum-fault benchmark for the given reference string and frame count. If several pages are never used again, any of them is an equally good victim.

08 / Bring the ideas together

Same starting point. Three reasons.

FIFO removes 1

It arrived first.

After: [4, 2, 3]

LRU removes 2

It was used least recently.

After: [1, 4, 3]

Optimal removes 3

It will be needed furthest ahead.

After: [1, 2, 4]

“Now we can see the difference: FIFO remembers arrival, LRU remembers recent use, and Optimal looks ahead.”

Over the full string 1, 2, 3, 1, 4, 1, 2, 3: FIFO = 7 faults, LRU = 6 faults, Optimal = 5 faults. Let’s test that together.
Teacher notes · how to explain this

Ask students to explain a victim choice in a full sentence, using the relevant rule. These totals apply to this example; do not claim LRU always beats FIFO.

The experiment

Trace every decision.

“Before I click Next reference, tell me: is this page already here? If not, is there an empty frame? If the frames are full, which page does our rule remove?”

Enter nonnegative page numbers. Step through a trace or reveal it all. The comparison uses your full reference string.

Frame positions stay fixed; “—” means an empty frame.

Teacher notes · how to explain this

Run FIFO first and reveal one request at a time. Have students predict the fifth request. Restart with LRU, then Optimal. Ask students to record faults and explain each victim. Fault rate is faults divided by total requests; for Optimal here, 5 ÷ 8 = 62.5%.

09 / Extend the discussion

More frames can mean more faults.

“You might expect that giving a program more frames always reduces faults. Let’s see why we must check that assumption.”

Belady’s anomaly can occur with FIFO.

Try 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5. FIFO produces 9 faults with 3 frames and 10 faults with 4 frames.

LRU and Optimal are stack algorithms: with a consistent tie policy, their resident sets are nested as frame count grows. They do not exhibit Belady’s anomaly.

Fault rate = faults ÷ references. Hit rate = hits ÷ references. Real performance also depends on fault latency, dirty-page writeback, and policy overhead.

10 / Your turn to explain

“Let’s finish by explaining the rules in our own words. Then try this question.”

Which policy needs future knowledge?

Discussion: Why not always use Optimal?

Real systems do not generally know the future reference string. Optimal is useful for comparing practical policies against a best-case fault count.

Practice: Trace 1, 2, 1, 3, 1, 2 with two frames

FIFO: 5 faults. LRU: 4 faults. Optimal: 4 faults. Explain which page each policy evicts when page 3 arrives.

Exit ticket: explain the difference between arrival order and access recency, then create a reference string where FIFO and LRU choose different victims.
11 / Close the lesson

One question.
Three ways to answer.

FIFO remembers arrival. LRU remembers use. Optimal knows the future.

Change one variable at a time in the simulator: the reference string, number of frames, or replacement policy. Predict the result before revealing it.
